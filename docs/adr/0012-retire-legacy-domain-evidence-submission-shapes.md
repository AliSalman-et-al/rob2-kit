# Narrow items/evidence_by_question/candidate_dispositions to visual-only evidence

`submit_domain_evidence` carried five mutually-exclusive ways to submit evidence: `passages` (the current review-then-freeze contract) plus four legacy shapes (`items`, `evidence_by_question`, `candidate_dispositions`, `conflicts`) kept for back-compat. Fixing #135 (the `review_revisions`/`passages` freeze bug) required auditing all three call sites that read post-resolution request state, which surfaced that `items`, `evidence_by_question`, and `candidate_dispositions` are already silently overwritten by `_resolve_evidence_passages` whenever a caller submits `passages` — so, for real MCP callers using the modern contract, direct input to those three was already discarded.

We initially planned to drop MCP's acceptance of all three as external parameters entirely. Auditing `tests/test_issue114.py::test_complete_with_limitations_evidence_remains_qualifying` before deleting it surfaced that this would delete real capability, not just back-compat weight: an inspected Visual candidate (a table or figure, returned by `inspect_visual_candidate`) has no `passages`-equivalent citation path — `EvidencePassageInput.unit_id` only accepts a canonical *text* unit from the search index, and visual inspection never materializes one. `items`/`evidence_by_question`/`candidate_dispositions` are the only way to cite inspected visual material as structured, frozen Evidence.

Decision: keep all three as MCP-accepted external parameters, but narrow their accepted content. `_validate_visual_evidence_items` (replacing the removed `_validate_legacy_evidence_items`) now rejects any `items` reference that isn't a valid `VisualTranscription` — the legacy `EvidenceClaim`-shaped item, which duplicated what `passages` already does for textual material, is retired. `conflicts` stays as caller-facing input, needed to link a superseded item to its replacement.

Follow-up (closed): the note above about `passages` + `conflicts` being mutually exclusive turned out to be a two-layer gap, not one. `validate_evidence_inputs` blocked `conflicts` alongside `passages`, but `EvidencePassageInput` also had no `superseded_by` field and rejected `SUPERSEDED` outright — so relaxing the mutual-exclusivity check alone would not have made the combination constructible. Fixed by: dropping `conflicts` from `validate_evidence_inputs`'s mutual-exclusivity check; adding `superseded_by` to `EvidencePassageInput` and allowing `SUPERSEDED` in its disposition check (mirroring `EvidenceConsiderationInput`); wiring `superseded_by` through `_resolve_evidence_passages`; deferring the conflicts-binds-frozen-items check in `_validate_domain_evidence_submission` to the post-resolution pass (`enforce_non_empty`), since resolved item IDs don't exist yet on the pre-check pass; and scoping `_freeze_domain_evidence`'s per-question `conflicts` to only the conflict groups fully contained in that question's item set, since a submission-wide `conflicts` was previously attached unfiltered to every per-question bundle, including ones holding neither linked item. See `tests/test_issue135.py::test_passages_based_superseded_disposition_with_matching_conflicts_is_accepted`.

This is still a breaking change to the MCP tool's parameter contract (textual legacy items are rejected outright) with no back-compat shim, accepted because the project is in active early development with no external callers to preserve compatibility for.
