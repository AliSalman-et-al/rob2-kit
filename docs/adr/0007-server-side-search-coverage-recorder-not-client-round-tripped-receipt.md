# Search coverage is server-side recorder state keyed by business identity, not a client-round-tripped receipt

Issue #127 found that the `passages` and `no_information_basis` branches of `submit_domain_evidence` were structurally unusable: both require a complete `SearchCoverageReceipt`, but no MCP-facing tool ever constructed or returned one for a caller to submit back, and the receipt's `recorder_proof`/`guidance_release_id` fields made hand-assembly impossible even in principle. `SearchCoverageRecorder` — the accumulator that produces a valid receipt — already existed fully built and unit-tested; it was simply never instantiated by the request handlers. We reject exposing the full receipt object through the client contract (issue's candidate direction 1) in favor of holding `SearchCoverageRecorder` instances server-side in the long-lived `RunEngine` process, keyed by `(run_id, result_id, domain_id, sq_id)` — business identity, deliberately not the opaque `WorkToken` itself: `search_evidence` accumulates into the recorder for the active scope as calls come in, and `submit_domain_evidence` looks up and freezes that state instead of reading `request.coverage_receipts`, which is removed from the request contract entirely. Keying on business identity rather than the reissued token is what lets ADR-0008's reroute carry forward already-accumulated progress after a `WorkToken` is reissued; keying on the token itself would have orphaned that state on every reroute. This still matches the spirit of the existing `work_token` precedent — an opaque value the caller never constructs or interprets — and eliminates the `guidance_release_id` format mismatch as a side effect rather than requiring a separate fix for it. Accumulated-but-unfrozen recorder state is intentionally not durable across a Harness disconnect/process restart — the glossary's Preparation checkpoint boundary stops at each Domain's frozen Evidence, not intermediate search rounds, so a resumed session simply re-issues `search_evidence` calls (cheap, idempotent, read-only) rather than reconstructing prior progress. `search_evidence` responses gain a read-only coverage-progress indicator (completed passes/seed families, whether the freeze gate is currently satisfied) so an agent can tell before attempting a freeze whether it has searched enough, without reintroducing a client-constructed object.

## Consequences

The *persisted*, post-freeze `SearchCoverageReceipt` stored in a Domain's Evidence Bundle keeps its full current shape (`result_spec`, `source_inventory`, `parse_record_hashes`, `guidance_release_id`, `resume_*`, `recorder_proof`) even though the request contract no longer carries one — those fields are accidental complexity for a caller who never constructs the object, but they remain load-bearing for a Verification archive that must audit a Result's evidence trail portably, outside a live `RunEngine` process. Test helpers that hand-assembled receipts via private engine internals (`tests/test_input_reconciliation.py::_complete_empty_receipts`/`_complete_passage_receipts`) are removed in favor of tests that drive the real `search_evidence` → `submit_domain_evidence` path.
