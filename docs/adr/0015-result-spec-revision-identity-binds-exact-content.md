# ResultSpec revision identity binds exact content across Runs

Issue #148 exposed two shared-ledger defects: ResultSpec lookup inferred the first Run in the Project, and repeated declared ResultSpecs could use the same entity and revision identities for different canonical content because their observation times differed. We require `(entity_id, revision_id)` to identify exactly one canonical byte sequence within a Project ledger. Declared revision IDs therefore derive from the complete non-circular revision preimage, including actor and observation time; observing the same declaration in a later Run creates a new ResultSpec revision. All ResultSpec lookup is explicitly scoped by `run_id`.

Freezing records the exact ResultSpec revision already held by the Run and never mutates it to infer `supersedes`; supersession must be assigned when a revision is created. Each Run records its own freeze event, keyed by its Run, Result, and revision identities, while the artifact store may still deduplicate identical bytes. Replaying any ledger operation key with an identical transition is idempotent, but replaying it with different content is a Run integrity failure.

We reject Run-scoping ResultSpec entity identity because a Result is a stable scientific identity rather than a Run-owned object. We also reject excluding observation metadata from canonical hashing because references and archives must bind exact bytes, and moving observation metadata out of ResultSpec because that would require a broader schema migration. Existing ledgers that contain one ResultSpec revision identity bound to different content fail integrity preflight; the Project is in active early development, so we accept updated revision IDs, hashes, signatures, traces, and fixtures without a compatibility or migration layer.
