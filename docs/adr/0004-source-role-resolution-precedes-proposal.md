# Source-role resolution runs before proposal generation, as its own operation

Investigation of issue #119 found two compounding bugs in the existing order: `submit_source_classification` ran *after* `confirm_run_definition`, and separately, it never wrote its submitted roles back into `SourceDescriptor.roles` — so `_classify`'s pre-review output was the only role value that ever existed for a run's lifetime, and it was already load-bearing pre-confirmation: `validate_result_sources` could hard-fail proposal submission on a missing primary-report role, and `_preferred_candidate` chose which protocol/SAP a proposal showed as "preferred," both reading the unreviewed cue. We move Source-role-candidate resolution to a required step between ingestion and `submit_run_proposal`, so nothing that can hard-fail or bias a proposal reads an unaccepted role again. `validate_result_sources` now requires an accepted disposition, not a cue, and `Source criticality` is recomputed from the resolved candidate instead of being fixed once at ingestion. Because the operation's contract changed from "declare final roles" to "accept/reject/leave-unresolved a Discovery candidate," it gets a new operation name rather than reusing `submit_source_classification` for a different meaning. Result-candidate and Registry-candidate resolution are deliberately *not* moved — they already resolve consistently through `RunProposalSelection` at proposal/confirmation time, and only Source-role had the ordering bug.
