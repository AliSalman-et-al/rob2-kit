# Retire the HMAC-signed cursor codec in favor of a server-side lookup-table token

`location_handle`, the search-pagination cursor, and the read-continuation cursor were all issued through `_SignedCursorCodec`: a self-verifying HMAC-signed base64 envelope, independently checkable with no server memory. That design is the right tool when a cursor might be presented to a *different* server instance than the one that issued it — classic stateless-API pagination-token design. It does not match this server's actual shape: exactly one `RunEngine` is constructed per MCP server process (`interfaces/mcp/server.py`), and that same process is the sole issuer and sole verifier for every cursor and handle for the run's lifetime. Cross-process portability was the property the HMAC design bought, and nothing exercises it.

The practical cost of the mismatch was ergonomic, not correctness: `location_handle` values were up to 4096-character opaque blobs routed through free-text MCP tool-call arguments — exactly the channel where an LLM caller's token-level transcription errors happen (dogfood item #10, GitHub #126). Aliasing a short token in front of the blob would have fixed the transcription surface while keeping two representations of the same concept in sync. We retired the codec instead: `location_handle`, the search cursor, and the read cursor are now short `kind`-prefixed tokens (`loc:`, `cur:`, `read:`) looked up against a row in a new `evidence_cursor_token` table in `evidence.sqlite3` — the same trust boundary as the file that used to hold the HMAC secret (the `evidence_cursor_secret` table it replaces is dropped; nothing signs or verifies a MAC anymore). Staleness detection is unchanged in substance — snapshot/fragment-identity comparison — just expressed as a `SELECT` and a field comparison instead of MAC verification. A lookup miss (unknown token) is now distinguishable from a found-but-stale row, which the self-verifying blob could not cleanly express.

## Considered Options

**Alias-in-front-of-the-blob**: keep `_SignedCursorCodec` as the real mechanism, add a short caller-facing alias that the server resolves back to the full signed cursor. Rejected: this is strictly worse than retiring the codec given the single-process finding above — it solves the same ergonomics problem while keeping the HMAC/base64 envelope machinery (~40 lines) and a second representation of every cursor to test and keep in sync, for a portability property nothing in this deployment shape uses.

**Location handle only, leave the pagination/read cursors on the HMAC codec**: narrower blast radius, since the original dogfood complaint was specifically about hand-transcribed `location_handle` values, not cursors an agent copies verbatim from a prior tool response. Rejected in favor of retiring the codec everywhere: all three cursor kinds share the same codec and the same trust boundary, so keeping two parallel mechanisms (short lookup for handles, HMAC blob for cursors) would be more moving parts than unifying on one, for a fix that costs about the same either way.
