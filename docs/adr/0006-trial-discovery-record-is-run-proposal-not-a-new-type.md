# `Trial discovery record` reuses `Run proposal`'s whole-snapshot revisioning; it is not a new type

ADR-0003 introduced `Trial discovery record` as the container for a Trial's Source-role/Result/Registry candidates, and `CONTEXT.md` described it gaining "a new revision whenever a contained candidate's disposition changes" — wording that reads as independent per-candidate revisioning, the same pattern `EvidenceReviewRevision` already uses for post-confirmation evidence review. A follow-up grilling session, informed by `docs/research/advisory-discovery-candidates.md`, checked that assumption against the codebase's two existing precedents and against what downstream consumers actually need. `ResultCandidate` and `RegistryCandidate` already work today as plain structs embedded in the single `RunProposal` snapshot, with disposition on a sibling `RunProposalSelection` and the whole proposal superseding atomically via `proposal_token`/`supersedes_proposal_id`. No consumer that reads discovery state — `validate_result_sources`, `_preferred_candidate`, Source criticality, the evidence-index rebind fingerprint — needs one candidate's history independent of the others; each reads "the current resolved set" as a whole. Independent per-candidate revisioning is proven necessary for Evidence review specifically because of scale (many claims across many signaling questions, each needing separately invalidatable dependencies); that justification does not transfer to a Trial's small, once-resolved set of discovery candidates. We therefore keep `Trial discovery record` inside the whole-snapshot `RunProposal` rather than building a second, independently-revisioned type that would always change in lockstep with it. Source-role candidates may originate in the earlier `ProjectInitialization`, but that pre-proposal inventory is not itself the Trial discovery record. `RunProposalSelection` carries the shared disposition shape, and `Discovery candidate disposition`'s `superseded` state is derived at read time from the accepted selection in a candidate's slot rather than stored separately: one explicit review establishes both the accepted candidate and every superseded alternative, so there is exactly one source of truth instead of two that could drift apart.

ADR-0020 refines the lifecycle boundary without changing the whole-snapshot decision: `ProjectInitialization` is a pre-proposal inventory used for Source-role review, not another representation of the Trial discovery record. The Trial discovery record begins with the first `RunProposal`, issued only after Source-role resolution and completed Proposal discovery review, and then continues to supersede atomically as dispositions, promotions, and Result mappings change.
