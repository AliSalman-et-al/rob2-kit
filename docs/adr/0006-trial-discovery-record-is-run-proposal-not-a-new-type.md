# `Trial discovery record` reuses `Run proposal`'s whole-snapshot revisioning; it is not a new type

ADR-0003 introduced `Trial discovery record` as the container for a Trial's Source-role/Result/Registry candidates, and `CONTEXT.md` described it gaining "a new revision whenever a contained candidate's disposition changes" — wording that reads as independent per-candidate revisioning, the same pattern `EvidenceReviewRevision` already uses for post-confirmation evidence review. A follow-up grilling session, informed by `docs/research/advisory-discovery-candidates.md`, checked that assumption against the codebase's two existing precedents and against what downstream consumers actually need. `ResultCandidate` and `RegistryCandidate` already work today as plain structs embedded in the single `RunProposal` snapshot, with disposition on a sibling `RunProposalSelection` and the whole proposal superseding atomically via `proposal_token`/`supersedes_proposal_id`. No consumer that reads discovery state — `validate_result_sources`, `_preferred_candidate`, Source criticality, the evidence-index rebind fingerprint — needs one candidate's history independent of the others; each reads "the current resolved set" as a whole. Independent per-candidate revisioning is proven necessary for Evidence review specifically because of scale (many claims across many signaling questions, each needing separately invalidatable dependencies); that justification does not transfer to a Trial's small, once-resolved set of discovery candidates. We therefore fold `Trial discovery record` into `RunProposal`/`ProjectInitialization` directly — a new `source_role_candidates` field alongside the existing candidate lists, extending `RunProposalSelection` with `source_id` so all three candidate types share one disposition shape — rather than building a second, independently-revisioned type that would always change in lockstep with the first. `Discovery candidate disposition`'s `superseded` state is derived at read time from the accepted selection in a candidate's slot, the same way pairing-level disposition is already computed today, rather than stored as its own field: one explicit review (an accept) establishes both that candidate's acceptance and every other candidate's supersession at once, so there is exactly one source of truth instead of two that could drift apart.
