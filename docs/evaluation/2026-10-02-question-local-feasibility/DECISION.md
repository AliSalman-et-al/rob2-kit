# Question-local workflow feasibility

Decision: **do not introduce staged signalling-answer state in this pass**. Retain ADR 0036. No runtime, pack, model-facing guidance, scientific answers, or benchmark records changed; no inference ran.

## Before and proposed after

Before: `get_domain_context` exposes the approved Result, evidence, comparison cards and all Domain questions. `save_domain_judgment` directly exposes a closed typed `list[DomainSaveAnswer]`; it validates the complete active path, resolves provenance, and atomically commits one Domain. Revision is an explicit exact-checkpoint supersession; review and overall state are invalidated/recomputed from complete checkpoints. There is no generic dispatcher hiding the answer schema.

Candidate after: expose one active proposition and its guidance; accept one typed answer; persist accepted answers; compute the next active question using the existing official `active_questions`; assemble and compute the Domain only when its path is complete. A prior-answer revision must invalidate newly inactive answers, require fresh assessment if a discarded branch becomes active again, and block stale Domain/overall review until the replacement path completes. Independent answers should not be discarded merely because another answer changes. Preserve original answer revisions and citations for human audit and independently verified export. No rule may infer an answer from source wording or reference labels.

This candidate is technically feasible and reduces each submission from five answer objects to one. In the captured An call, the full answers array is 5,426 compact JSON bytes versus 761–1,450 bytes per answer. All question cards occupy 19,026 bytes of the first context's roughly 56 KB; a focused question view could reduce initial exposure. These are payload measurements, not measured comprehension, inference usage, or scientific gains.

## Existing functionality and irreducible new work

`active_questions` already owns branching and `evaluate_domain` already owns the deterministic tables. Neither accepts an incomplete path as a Domain assessment. The current public boundary provides no incremental signalling save. `WorkingDraft` holds an optional provisional answer, text and source locators; it is explicitly unfinished, non-authoritative working memory. `save_working_checkpoint` replaces a Trial's notes and does not validate canonical Evidence references, commit scientific answers, advance signalling questions or preserve accepted-answer revision history. Exposing these notes as accepted answers would misrepresent their authority.

A real question-local workflow therefore needs accepted partial-answer storage, source/Result/pack binding, concurrency/retry identity, explicit current question and backtracking, incomplete revision/review handling, and exportable correction history. Current bundle promotion and independent verification follow complete Domain histories. A disposable cursor or temporary handle table cannot supply the requested durable audit. This is a substantive new transaction lifecycle, not an exposure of an already-existing question save. Calling the whole-domain validator with one answer produces missing-active-question repairs; synthesizing unasked answers to satisfy it would violate scientific ownership.

## What the exact failures establish

`an-question-projection.json` validates each actual first-call answer independently with the current public model. **All five still fail**: their ordinary citation `evidence` is an array where one handle is required. Removing the outer answers list does not remove that inside-question distinction. Direct counterclaim handles were well formed. Each answer in the model's second call passes shape validation; its remaining rejection is D2.6's definitive No alongside explicitly unresolved observed-versus-missing outcome and exclusion/grouping premises. The failure is local to that proposition, not a mistaken official branch or ambiguity about which proposition the server rejected.

The original MONARCH failures in the linked immutable inventory likewise concern tags, roles, scalar/index counterclaims and required fields inside individual answers. The separated public contract fixed some of that clerical reconstruction; current frozen MONARCH successfully saved D3. The original and current An calls remain unmodified and are not translated into successes. Shape validation is not scientific validation.

Question-local state would retain the other valid shapes during repair, reducing resubmission of their prose. It would not by itself correct the shared citation-shape mistake, or establish D2.6's missing-only allowance and D2.7's conditional potential-impact warrant. The An paragraph was already delivered, cited, and distinguished from affirmative trial-context causation in the last run. The remaining capability bottleneck is applying the scientific premise thresholds and uncertainty calibration after reading the right evidence. Definitive No with an unresolved decisive premise was correctly rejected; changing it mechanically to ProbablyNo would not establish a defensible inference.

## Reason for retaining the current workflow

The real benefit demonstrated here is smaller per-call exposure and retention of independent drafts, not prevention of the observed failures. A staged workflow increases the minimal successful save count from one to five for this active path and introduces the durable correction lifecycle above. We have no question-local behavior trace showing that it resolves the local premise error or the repeated within-question construction error. Given the requested minimal scope and usage conservation, this evidence does not justify replacing the tested transaction boundary now. This is not a claim that question-local assessment cannot help, or that such a workflow is too difficult to implement. It is a decision against adding accepted intermediate state without evidence that this mechanism addresses the current blocker.

No alternate API, compatibility wrapper, text heuristic, question-specific answer default, corpus substitution or new scientific policy is introduced. A future decision to adopt this candidate should explicitly revise ADR 0036 and test the new correction/export lifecycle, rather than presenting working notes or a one-question projection as a saved answer. Existing safeguards are checked offline in this pass; they are not evidence that an unimplemented candidate meets those safeguards.
