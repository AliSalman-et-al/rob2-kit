# Decision: do not run the archived one-boundary compaction comparison

**No-go.** The supported host can fork a completed turn, but the relevant Domain boundaries are inside a single completed turn. No supported item-level fork/rewind operation is exposed by the locally generated protocol. We cannot create comparable D3-to-D4 histories from these preserved sessions without unsupported history manipulation or rerunning several Domains. The retained evidence also does not demonstrate a downstream scientific judgment error caused by history. Do not implement a canonical-only reset, launch compaction, replay a full assessment, or substitute a citation error for proof of an incorrect risk judgment.

This closes the prior conditional compaction direction for these archives. The existing source-selection/entailment failure is a more direct and smaller capability target, described below; no new adjacent-case audit or prompt addition is requested.

## Supported operation and why branch creation fails

The existing local `codex-cli 0.159.0` schema exposes:

- `thread/fork`: `threadId` and optional `lastTurnId`; the latter forks **through a completed turn, inclusive**. It does not accept an item ID or Domain checkpoint. `excludeTurns` changes response hydration, not which history is kept.
- `thread/compact/start`: only `threadId`; no deterministic handoff/replacement-history field. This operation may invoke inference and was not requested.
- `thread/items/list`: supports reading items by turn, not rewinding them. Item injection appends supplied items; it does not establish an authentic earlier provider context or remove the closed turn.

The normalized relevant schema descriptions/fields and SHA256s are in `host-fork-capability.json`; no new app-server or external request was made in this pass. Supported forks are conceptually safe for the original thread, but no fork operation was executed. No credentials or hidden session records were read/copied.

Forking EXSCEL through the earlier completed initial native turn would preserve a boundary before **any Domain save**, not the proposed D3-to-D4 boundary. Its six-call initial turn ended while D1 source/context recovery was unfinished. It lacks accumulated prior Domain judgments, so it does not isolate the hypothesis. Forking through the completed recovery includes already-saved D5 and finalization in history. Pairing that with a cloned earlier canonical workspace would silently mismatch history and scientific state. Truncating rollout JSONL or constructing injected pseudo-history would be unsupported and could alter approvals, hidden state and model configuration. Both are rejected.

If a future assessment deliberately stopped a completed host turn at a Domain boundary, two supported forks of that **same** idle turn could hold comparable history. Each would need a separate hash-identical disposable MCP workspace and explicit verified launcher routing; host thread forking alone does not isolate the MCP database. Model ID, effort, code/skill hashes, source hashes/projections, approved Result/review acknowledgment and canonical checkpoint bindings must remain identical. Do not inherit a shared writable original workspace. Those requirements cannot restore an item-level archive boundary here.

## Scientific criterion and the cost-control requirement

A genuine scientific outcome would be the presence or absence of a **falsified claim about scope, chronology or performed versus planned analysis**, or failure to retain material counterevidence when making a judgment. For this particular preserved EXSCEL downstream omission, the narrower measurable outcome is clause-level support fidelity: does the imputation-plan clause select a passage that actually supplies it, while preserving the plan/performance distinction and not claiming Figure S9 was read? Risk-label agreement and reduced tokens cannot count as success. This citation outcome alone would not warrant a clinical accuracy-gain claim.

A fair compaction test also needs a cost-matched extra-work control: baseline receives the **same checkpoint preparation, fresh context and recoverable source access**, plus the same allowance for an additional review response; treatment receives compaction instead of that extra review. Both get the same continuation budget, one attempt and no response-informed retries. The review control must use ordinary review instructions without expected facts, special retrieval leads or extra evidence. It tests whether any benefit exceeds simply spending comparable inference on reviewing the state.

Predeclare that “cost matched” means actual provider-priced inference spend for the extra review versus compaction within a narrow tolerance (for example 10%), including compactor input/cache/output and recovery overhead. If pricing or compactor usage cannot be observed, call it an equal-budget/extra-response control, **not a cost-matched result**, and do not attribute an effect specifically to shorter history. Summed input tokens or uncached tokens alone are not cash cost. Do not add model calls merely to force a match after seeing outcomes. Because the compactor accepts no budget or controlled summary input and its inference telemetry has not been verified here, this cost-matched comparison is not execution-ready. Extra review has a different reasoning operation; even matched spend would estimate the full compaction strategy versus extra review, not a pure isolated memory mechanism.

The previously recorded EXSCEL initial per-response input counts are request-size telemetry only. Its completed recovery's 5,856,513 summed input includes many repeated requests; it cannot reconstruct the boundary's semantic context. A broad native rerun to manufacture a forkable boundary would spend substantial inference on already-inspected Domains, with no demonstrated history-induced judgment error. That expected benefit is insufficient. Stop this direction now.

It can test whether the normal review recovers the unsupported clause's exact source and preserves uncertainty, compared with simply asking for an additional reread of the same materials. Expected benefit is a directly observable, bounded evidence-grounding capability with far fewer source/tool loops than an EXSCEL D1–D5 history rerun. It would require its own exact source-completeness preflight, frozen input and private criteria, and separate authorization; this decision does not prepare or launch it. It must not become another repeat factual quiz or impose a new production gate.
